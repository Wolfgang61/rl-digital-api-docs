## Erfolgreiches Beispiel: ePIL per PZN abrufen

Der folgende Ablauf zeigt eine erfolgreiche Nutzung der eCAPI v2 mit `curl`:
Zuerst wird ein OAuth2-Token angefordert, anschließend wird ein Arzneimittel über
seine PZN gesucht und die zugehörige elektronische Produktinformation (ePIL)
abgerufen.

### Voraussetzungen

Benötigt werden:

- ein für die eCAPI freigeschalteter OAuth2-Client,
- `curl` und `jq`,
- eine gültige PZN. Im Beispiel wird die in der OpenAPI-Beschreibung verwendete
  Beispiel-PZN `00094113` verwendet.

```bash
export BASE_URL="https://qa-digital.systems-tooling.de"
export CLIENT_ID="<client_id>"
export CLIENT_SECRET="<client_secret>"
export PZN="00094113"
```

Client-Secrets dürfen nicht in Quelltext, Repositories oder Logs gespeichert
werden.

### 1. Access Token anfordern

Der Token-Endpunkt akzeptiert gemäß OpenAPI sowohl
`application/x-www-form-urlencoded` als auch JSON. Die folgende Variante
verwendet das standardkonforme Formularformat:

```bash
TOKEN_RESPONSE=$(curl --fail-with-body -sS -X POST "$BASE_URL/ecapi/token" \
  -H "Content-Type: application/x-www-form-urlencoded" \
  --data-urlencode "grant_type=client_credentials" \
  --data-urlencode "client_id=$CLIENT_ID" \
  --data-urlencode "client_secret=$CLIENT_SECRET")

TOKEN=$(echo "$TOKEN_RESPONSE" | jq -er '.access_token')
export TOKEN
```

Eine erfolgreiche Antwort (`200 OK`) enthält ein Bearer-Token:

```json
{
  "token_type": "Bearer",
  "expires_in": 3600,
  "access_token": "<access_token>"
}
```

### 2. Arzneimittel über die PZN suchen

Für die Suche wird genau einer der Parameter `q` oder `org-id` verwendet.
Die Antwort ist ein FHIR-`Bundle` im JSON-Format:

```bash
SEARCH_RESPONSE=$(curl --fail-with-body -sS \
  "$BASE_URL/ecapi/v2/medicinal-product/search?q=$PZN&limit=5" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Accept: application/fhir+json")

echo "$SEARCH_RESPONSE" | jq .
```

Beispiel für eine erfolgreiche Antwort (`200 OK`):

```json
{
  "resourceType": "Bundle",
  "type": "searchset",
  "total": 1,
  "entry": [
    {
      "resource": {
        "resourceType": "MedicinalProductDefinition",
        "id": "mpd-12345",
        "name": [
          {
            "productName": "Example Medicinal Product"
          }
        ]
      }
    }
  ]
}
```

### 3. ePIL per PZN abrufen

Mit derselben PZN wird nun die ePIL abgerufen. Der Server liefert bei Erfolg
FHIR JSON (`200 OK`):

```bash
curl --fail-with-body -sS \
  "$BASE_URL/ecapi/v2/pil/pzn/$PZN" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Accept: application/fhir+json" \
  | jq .
```

Die Antwort enthält ein FHIR-Bundle mit den veröffentlichten Ressourcen der
ePIL, zum Beispiel:

```json
{
  "resourceType": "Bundle",
  "type": "searchset",
  "total": 1,
  "entry": [
    {
      "resource": {
        "resourceType": "Composition",
        "id": "comp-12345",
        "status": "final"
      }
    }
  ]
}
```

Die IDs und Inhalte in den JSON-Antworten sind illustrative Beispiele. Für
Produktivaufrufe müssen PZN und Client-Credentials durch gültige Werte der
jeweiligen Umgebung ersetzt werden.

### 4. Optional: Antworten mit ETag cachen

Die eCAPI liefert für die ePIL-Endpunkte einen `ETag`. Bei einer späteren
Abfrage kann dieser mit `If-None-Match` wiederverwendet werden:

```bash
curl --fail-with-body -sS -D pil.headers -o pil.json \
  "$BASE_URL/ecapi/v2/pil/pzn/$PZN" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Accept: application/fhir+json"

ETAG=$(awk 'tolower($1) == "etag:" { sub(/\r$/, "", $2); print $2 }' pil.headers)

curl -sS -D - -o /dev/null \
  "$BASE_URL/ecapi/v2/pil/pzn/$PZN" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Accept: application/fhir+json" \
  -H "If-None-Match: $ETAG"
```

Antwortet der Server mit `304 Not Modified`, bleibt die lokal gespeicherte
Antwort gültig und der Client verwendet `pil.json`. Bei einer geänderten
Repräsentation wird erneut `200 OK` mit dem aktuellen FHIR-Bundle geliefert.

### Erfolgs- und Fehlerfälle

| Situation | Erwartetes Ergebnis |
| --- | --- |
| Token wurde ausgestellt | `200 OK` mit `access_token` |
| Arzneimittel gefunden | `200 OK` mit FHIR-`Bundle` |
| ePIL gefunden | `200 OK` mit FHIR-JSON oder FHIR-XML |
| Repräsentation unverändert | `304 Not Modified`, leerer Response-Body |
| PZN unbekannt | `404` mit FHIR-`OperationOutcome` |
| Zu viele Anfragen | `429` mit `Retry-After`; danach warten und erneut versuchen |

Für alle Endpunkte muss der Client den `Authorization: Bearer <token>`-Header
senden. Die vollständigen Parameter, Antwortformate und Schemas stehen in der
[OpenAPI-Referenz](openapi/ecapi-v2.json).
